### [CONFIRMED | high] Context-switch guard fires on intra-task frame switches, training users to disarm it
- **Area:** src/store.ts `setActiveFrameGuarded` / `selectTask` / `resolveSwitch`
- **Description:** The guard was raised on *every* frame switch away from a dirty agent, ignoring

  modal. Compounded by the one-shot-ack finding (ux-design #1 / frontend): the fast path past the

  from the guard — including for genuinely risky cross-task switches.
- **Fix (shipped with this addendum):** (1) same-task frame switches (incl. both-Uncategorized, the
  null partition cell) are exempt — *unless* the two agents have dirty paths in common (real
  contention still guards); (2) `selectTask` to the agent's own task is never guarded (it's the path
  to its own Review tab); (3) "Proceed without review" is now a session-local skip — not persisted;
  new dirty paths beyond the acknowledged set re-arm the guard locally and clear the daemon ack (new
  `clear_reviewed` query, which unlike `clear_dirty` leaves the watcher accumulation intact); a
  hydrate tick can no longer disarm an agent that is dirty again. This also resolves the one-shot
  review-ack finding (ux-design: "Review ack is one-shot per agent").

## daemon-lifecycle

**Summary:** The daemon lifecycle layer is in strong shape post-f2abb7f: process-group kill with SIGTERM-grace-SIGKILL escalation, the durable cleanup ledger with boot replay, the boot orphan sweep, claim-first schedules, hello deadlines, and the exactly-once attach/repaint handoff under one state lock are all genuinely careful. The remaining defects cluster in three areas: (1) identity reuse — pty-N counters restart at 0 every daemon generation while idle-shutdown makes restarts routine, silently corrupting the durable session/graph records (the one high finding); (2) narrow-but-permanent wedges — a lost condvar wakeup that leaks the reader+PTY+fs-watcher forever, a non-panic-safe gc latch, and untimed blocking PTY writes inside the single-flight maintenance tick; (3) bounded contention — SQLite writes under the session state lock chained beneath the global sessions lock. Sub-bar items folded here: biased writer select can starve RPC responses during sustained PTY floods (bounded by the 128MB cap); DECCKM/mouse modes are not restored on reattach (mouse documented, cursor-key mode not); the watcher's gitignore is snapshotted once at spawn; the CACHEDIR.TAG memo is never invalidated; manual run_schedule sets last/next after firing (no claim-first like fire_schedule); reconcile_cleanups_on_boot deletes unparseable ledger rows without replaying them; a grandchild holding the PTY slave open keeps the reader blocked in read() (thread+fd leak until it exits); attach-steal between two connections is silent to the displaced client. I checked the idle-shutdown vs. concurrent-connect race and the shutdown unlink ordering: both are benign as written (decision-to-exit window is microseconds, and socket→token→lock unlink order means a successor can't interleave). Overall grade feel: B+ — hardened and thoughtfully commented, with one thesis-relevant durable-identity bug and a few permanent-wedge races left.

### [REFUTED | medium] Lost condvar wakeup: reader parked on backpressure can sleep forever after gc reap, leaking thread, PTY fd, and a live fs watcher
- **Area:** src-tauri/crates/taime-session-daemon/src/session.rs:784-793,852-854,476-483,751-769; manager.rs:2328-2339
- **Description:** The reader parks on `while st.paused { wait; if dead break }` — it checks `dead` only after a wakeup, and `finalize_exit` never clears `paused`. If the child exits while >2MB is un-acked and `reap_if_exited` completes (sets dead, notify_all) in the window where the reader is between loop iterations (lock released, not yet waiting), the notify is lost; the next tick's dead-sweep removes the session from the map, after which nothing ever notifies again. The reader thread sleeps forever holding Arc<SessionInner>: PTY master/child fds leak, and the SessionWatcher stays alive — its Weak upgrade succeeds, so fs events keep being recorded against the exited agent's key indefinitely (attribution pollution).
- **Evidence:** session.rs:788-792 checks `inner.dead` only after `resume.wait()`; the predicate `st.paused` is never falsified by finalize_exit (751-769) or reap_if_exited (476-483, notify without holding the state lock). manager.rs:2330-2338 removes dead sessions from the map, eliminating all future notifiers (kill/attach/detach/ack).
- **Fix:** Make the park predicate `st.paused && !inner.dead.load(..)`, and have finalize_exit set `st.paused = false` under the state lock before notify_all (the standard predicate-under-mutex condvar pattern).
- **Verifier notes:** The narrow condvar race exists (reap_if_exited's notify doesn't falsify `paused`; dead checked post-wait), but the claim's core premise is wrong: map removal does NOT eliminate future notifiers. conn.rs dispatches AckBytes/Detach/conn-close-detach on the connection's held Session Arc (conn.rs:115, 210, 233-237, 267-269), not via the map; both ack (session.rs:370-376) and detach (346-349) clear `paused` under the state lock before notify_all — unlosable wakes. A parked reader implies an attached client (paused set only at 853 under `if let Some(c)`), and finalize_exit's Exited frame makes the app pump drop its dedicated socket (daemon.rs:429-476, 554-558), triggering detach→unpause; app crash closes the socket the same way. The reader then sees EOF and finalizes; Arc/watcher/fds release. Only a forever-connected never-acking peer stalls it — identical to the deliberate flow-control park on live sessions.

### [CONFIRMED | medium] gc single-flight latch is not panic-safe: one panic in gc_tick silently disables all daemon maintenance forever
- **Area:** src-tauri/crates/taime-session-daemon/src/main.rs:278-294; manager.rs:2209-2218 vs 133-139,1619-1627
- **Description:** main.rs runs gc_tick on spawn_blocking and calls `m.end_gc()` only on the normal return path; the JoinHandle is dropped, so a panic anywhere in gc_tick (sessions/roles/tokens/last_activity `.lock().unwrap()` on a poisoned mutex, store `.conn.lock().unwrap()`, enqueue paths) is swallowed silently and `gc_running` stays true permanently. Every subsequent 250ms tick then skips: no dead-session reaping, no SIGKILL escalation, no quiet-window turn attribution, no inbox delivery, no status pushes, and no idle shutdown — a zombie daemon with zero diagnostics. The codebase already built the panic-safe `FlagGuard` drop-guard for exactly this and uses it for `schedules_checking`, but not for the gc latch.
- **Evidence:** main.rs:286-293: `spawn_blocking(move || { if m.gc_tick(..) {..exit..} m.end_gc(); })` — handle dropped, end_gc skipped on unwind. manager.rs:133-139 FlagGuard exists; manager.rs:1627 uses it only for check_schedules. manager.rs:2209-2218 try_begin_gc/end_gc have no guard.
- **Fix:** Hold a FlagGuard(&self.gc_running) inside gc_tick (or wrap the spawn_blocking closure body), and log if the join handle reports a panic.
- **Verifier notes:** Confirmed. main.rs:278-293 sets the latch via try_begin_gc, calls end_gc only on gc_tick's normal return, and drops the spawn_blocking JoinHandle; the crate has no panic hook, no catch_unwind, and no panic=abort, so an unwind is silently swallowed with gc_running stuck true — end_gc (main.rs:292) is the only reset in the crate. gc_tick (manager.rs:2322-2391) unwraps sessions/tokens/roles/assignments/last_activity locks and calls Store methods that unwrap conn.lock() (~40 sites), so a poisoned mutex from any other panicking task makes the next tick panic. Decisively, FlagGuard's own doc (manager.rs:131-138) says it guards "the gc tick + cron check... even on panic" but it is used only for schedules_checking (1627) — proving oversight, not design. Only nit: schedules/worktree-sweep/history-prune run outside the latch, so "all maintenance" slightly overstates; severity medium is correct.

### [CONFIRMED | low] Accept loop hot-spins on persistent accept errors (e.g. EMFILE)
- **Area:** src-tauri/projects... src-tauri/crates/taime-session-daemon/src/main.rs:318-325
- **Description:** On `listener.accept()` error the loop logs and `continue`s immediately. Persistent errors like EMFILE/ENFILE (plausible: each session holds a PTY master, child, watcher fds, plus per-connection fds, and the leaks above accelerate it) are not transient, so the loop spins at 100% CPU spamming stderr and never recovers fds. A short backoff sleep on error is the standard hardening and keeps the daemon (which owns live agents) degraded-but-calm instead of pegging a core.
- **Evidence:** main.rs:319-325: `Err(e) => { eprintln!(...); continue; }` with no delay — EMFILE returns instantly, so the loop busy-spins.
- **Fix:** On accept error, sleep ~100-500ms before continuing (optionally with a counter that logs once per window).
- **Verifier notes:** Confirmed. main.rs:319-325 does `Err(e) => { eprintln!(...); continue; }` with no delay on `tokio::net::UnixListener::accept()` (listener.rs:22). ## attribution

**Summary:** The attribution substrate itself is genuinely well-built: durable per-turn records with real wall-clock starts, plural ranked boundary signals (app checkpoint > OSC-133 > quiet-window) with zero-length-turn coalescing, batched fs-event transactions, transient-file filtering shared between watcher and diff, and a conservative worktree GC that provably never deletes unreviewed work. But the thesis-critical merge half of the pipeline is broken end to end: the UI sends symbolic merge targets ("main"/"self"/agent-id) that the daemon treats as literal directories, so Merge and Revert can never apply — and even with that fixed, untracked agent-created files have no hunks and are unmergeable, meaning the review gate has plausibly never completed a real merge since the Rust migration. "Nothing merges without Review" is enforced purely by UI placement: the daemon consults no review state on apply, any same-uid process (agents included) can call it, and agents can write the main tree directly with git, undetected, since attribution sensors stop at the worktree boundary. Shared mode — the default for every schedule fire — durably attributes the user's and other agents' edits to each watching agent. Below the findings bar: stale review acks aren't invalidated daemon-side on new fs events (the app's dirty badge compensates), debounce timing can attribute a turn's last file writes to the following turn, record_turn drops causes/offsets/exit codes despite schema columns existing for them, daemon-wide (unscoped) fs contention can cross-match identical relative paths from different workspaces, and the worktrees_gced set plus per-restart GC re-probing are minor wastes. Grade feel: recording A−, review/merge enforcement D — the flagship loop fails at exactly the step the product is named for.

## security

**Summary:** The cross-USER boundary is solid: the socket is born 0600 under a 0700 dir, every accept is peer-uid validated (getpeereid/SO_PEERCRED), and the frame codec caps allocation (16 MiB) on both the main path and the MCP shim. git is always invoked via arg-vectors (no shell) with `--` separators where untrusted paths reach positional args, and the AppleScript clipboard path is well-defended (control-char + leading-dash rejection, fixed class allowlist, no shell). delete_directory has real catastrophic-path guards, workflow runs are capped (8), and HELLO/RPC timeouts plus a response-backlog cap close the obvious same-user DoS vectors. The weaknesses are all inside the same-USER trust model, which the code treats as fully trusted while agents run unsandboxed (`--dangerously-skip-permissions`/`--yolo`). The sharp edges: orchestration tools are daemon-wide (no workspace scoping), the raw control protocol bypasses the curated/authenticated MCP tool surface (sender spoofing via SendMessage, destructive Query ops), the attach token does not actually isolate co-resident processes despite comments implying it does, and `assign`/`run_workflow` accept unvalidated working directories. Below the bar: SendMessage/Query authorization is "any handshaken connection"; blackboard `key` is not length-capped (value is); data-dir/worktree dirs are not chmod-hardened like the runtime dir; the MCP token is written to ~/.gemini/settings.json / claude argv (harmless cross-user because the uid gate still blocks the socket).

## product-gaps

**Summary:** Taime's front half of the loop is genuinely strong: launch (two-step task-first dialog), watch (status grammar, dirty counts, command palette, context-switch guard, focused AgentDetail with Terminal/Console/Diff/Activity), and per-hunk attributed review with merge/revert per worktree plus a task-level aggregate lens and merge queue — that last part is ahead of most of the field. Overall: an A- substrate with a B- product shell — the highest-leverage fixes are finishing the merge (commit/PR with provenance) and exporting attribution, which together convert the differentiator from a screen into an artifact.
